# Linux 日志空间回收页（Flask）

删掉的日志还占着磁盘，是因为还有进程拿着它当初打开的文件描述符（inode 未释放）。
这个页面会：

1. 检查本地写入进程**实际打开的文件**（`/proc/<pid>/fd`），找出已删除但仍被持有的日志；
2. 以 **设备号 + inode** 去重（多进程共用一份、单进程持有多份都算一份）；
3. 按 **实占块数**（`st_blocks × 512`）而不是文件表观长度计量；
4. 输入要腾出的 MiB，找出**覆盖某份日志全部持有者**的最小进程名单；
5. 确认时重新校验；状态变了就提示重算、本次不执行；
6. 有效时让选中的进程**重开现用日志并继续写**；重开失败的进程继续用原句柄；
7. 复查原 inode，显示按确认时占用计的已释放量和仍占用的日志与持有者。

## 快速开始（Docker Compose）

```bash
docker compose up --build
# 打开 http://localhost:8080
```

容器内会启动 **8 个演示写入进程**（上限 8），它们与 Web 进程同 UID、同 PID 命名空间，
因此页面能读到它们的 `/proc/<pid>/fd` 并通过 Unix socket 让它们重开日志：

| 进程 | 持有 |
| --- | --- |
| `shared-a` / `shared-b` / `shared-c` | 共用 `shared.log` 一份（必须三者都选中才能释放） |
| `multi-a` | `multi-a-{1,2,3}.log` 三份 + `shared-alt.log` |
| `multi-b` | `multi-b-{1,2,3}.log` 三份 + `shared-alt.log` |
| `solo-a` / `solo-b` / `solo-c` | 各自一份日志 |

页面上的“轮转现用日志”会把正在写的文件改名，“删除旧日志”会 `unlink` 这些 `.rot` 文件；
写入进程不会收到任何信号，仍用原句柄继续写——这就造出了“已删除但占磁盘”的日志。

不使用 Docker：

```bash
python3 -m pip install -r requirements-dev.txt
export LOG_ROOT=/tmp/logs STATE_DIR=/tmp/state
python -m demo.seed            # 启动 8 个写入进程并制造一代已删除日志
python -m logreclaim.app       # 默认 http://127.0.0.1:8080
```

## 规格与行为细节

**计量口径**：`st_blocks × 512`。稀疏文件、预分配文件按实际分配算，不按 `st_size`。
同一 inode 被多个 fd / 多个进程打开只计一次。

**“全部持有者”规则**：只要还有一个持有者进程没被选中，内核就不会释放该 inode 的块，
因此该日志不计入计划的可释放量。多进程共用的日志会显示所有持有者，并标明哪些在名单内。

**最小名单**：在“每份日志必须由全部持有者覆盖”的约束下做最小基数集合覆盖；
同等进程数下优先释放更多字节。进程数 ≤18 时精确搜索，否则退化为贪心覆盖。

**无解**：如果覆盖所有持有者后仍达不到目标（或某份日志还有其它硬链接、持有者不属于可控制进程），
页面会直接说明原因，并给出全选名单下的最大可释放量。

**确认时的校验**（任一成立即提示重算、不执行）：

- 计划覆盖的旧日志已不再被打开，或其路径 / 持有者 / 链接数已变化；
- 名单中的进程已退出、PID 被复用或不再持有旧日志；
- 原名单按**当前**占用已达不到目标；
- 按当前占用存在更小的名单（原名单不再最少）。

**执行**：对每个选中进程，通过它自己的控制 socket 发送 `reopen`，进程以
`O_WRONLY|O_CREAT|O_APPEND` 重新打开自己的现用日志路径（旧文件已删除时即新建文件），
然后继续写入。打开失败的句柄保持原样，进程继续写原来的 inode。

**执行后复查**：按原 `(dev, ino)` 逐一确认，用确认时的实占块数汇总已释放量；
仍存在的 inode 会连同当前持有者一起列出。

## 目录结构

```
logreclaim/
  procfs.py      只读的 /proc 解析：fd、inode 身份、st_blocks、进程身份
  planner.py     纯逻辑：去重、持有者覆盖、最小集合覆盖
  scan.py        把 /proc 快照转成计划记录
  controller.py  校验、快照、执行、轮转/删除
  agents.py      写入进程注册表与 Unix socket 控制通道
  app.py         Flask 路由
  templates/     页面
demo/
  writer.py      持续写日志的演示进程（支持 shared / multi / single）
  supervise.py   启动 8 个演示写入进程
  seed.py        非 Docker 环境的一键造数
tests/
  test_planner.py      纯逻辑单元测试
  test_integration.py  真实 /proc、真实 unlink、真实进程的端到端测试
```

## 配置

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `LOG_ROOT` | `/data/logs` | 演示写入目录，也是页面展示用的日志根 |
| `STATE_DIR` | `/data/state` | 写入进程注册表、socket、运行日志 |
| `MAX_WRITERS` | `8` | 可控制的演示进程上限（最大 8） |
| `DEMO_WRITERS` | `1` | 容器启动时是否拉起演示写入进程 |
| `DEMO_WRITERS_COUNT` | `8` | 拉起数量 |
| `SCAN_SCOPE` | `agents` | `agents` 只扫描已注册的写入进程；`host` 先出受控进程首屏，全机扫描在后台进行 |
| `PLAN_TTL_SECONDS` | `900` | 计划的确认有效期 |
| `WRITE_CHUNK` / `WRITE_INTERVAL` | `8192` / `0.25` | 演示写入节奏 |

### `SCAN_SCOPE=host` 的两阶段扫描

用 `SCAN_SCOPE=host` 启动（`SCAN_SCOPE=host docker compose up --build`，或在 `.env`
里设置）后，首页不会被一次全机扫描阻塞，而是分两阶段：

1. **受控首屏（立即返回）**：只枚举已注册写入进程持有的已删除日志，包含每份日志的
   原路径、实占块数和已知持有者（含 fd 槽位），页面顶部明确标注“全机核对尚未完成”。
2. **后台全机扫描**：扫描在守护线程中遍历全部可见进程；完成后整表替换为全机结果，
   页面通过 `/scan/status` 轮询并自动刷新。扫描失败时保留首屏、展示错误并提供
   “重试全机扫描”按钮（`POST /scan/retry`），首页自身不会反复自动重启失败的扫描。

**表纪元（table epoch）与变更屏障**：轮转、删除旧日志、确认执行回收都会让表纪元加一，
并废弃任何在途的后台扫描。首页下一次接受的全机结果只能来自操作结束**之后**开始的扫描：
旧扫描即使卡住，新一轮扫描也能独立完成；迟到的旧结果在发布前会比对纪元/轮次并被丢弃，
不可能盖过新表。

**计划与确认始终实时全机扫描**：`/plan` 与 `/confirm` 各自同步读取一次当前 `/proc`，
从不复用后台缓存表，因此其计算与校验口径永远是操作当时的全机实况。确认执行结束后同样
推进表纪元，后台表随之失效。

> 生产环境把 `SCAN_SCOPE=host` 时，非本页可控制的进程只作为持有者展示，
> 它们不会被选中，因而相关日志不会被计入可释放量。

## 限制

- 需要与目标进程同 UID（或 root）才能读取其 `fd` 表；读不到的进程数会在页面上提示。
- 只处理 `write()` 型日志；使用内存映射（`mmap`）写日志的进程，重开文件不会解除映射。
- 只统计仍有进程持有的已删除文件；已被所有进程关闭的文件由内核自动回收，无需本页。
- 执行只会重开进程注册的现用日志路径，不会 kill 进程、不会截断正在写的文件。
